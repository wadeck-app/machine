## poc-node (`C:/Workspace_Other/poc-node`)

- Fastify 5 + `@fastify/websocket`, PM2 single instance, Infomaniak shared Web Hosting, `https://<relay-host>`.
- `/relay-ws` is one-way (server to listener) and tied to webhook sources; no registry, presence or peer signalling today.
- Auth: 256-bit bearer tokens; "no roles by design", any token reads the whole key-value store (verified in `docs/THREAT_MODEL.md`).
- WebSocket on the Infomaniak proxy WORKS (verified 2026-11-13): queue's relay client holds `wss://<relay-host>/relay-ws` since 2026-10-31 (`~/.config/queue/relay-daemon/relay.log`: 132 authentications, 144 closes, connections of 6+ hours, GitHub events received minutes before the check); an unauthenticated upgrade from Node 22 opens. Documented in poc-node `DEPLOY_INFOMANIAK.md` ("Verified on the live host"). Still unmeasured: proxy idle timeout, throughput, cause of the closes.
- poc-owner (agent report, not re-verified): server pings every 30 s, reaps after 60 s without pong; 64 KiB max frame; 500 total / 20 per IP connections; no per-socket bandwidth cap; backpressure above 1 MiB SKIPS events (unacceptable for opaque frames); no peer-to-peer routing exists; every push to main restarts the process and drops all sockets; an Ed25519-challenge route would be new code and must reuse the attempt limiter and pre-auth caps.
- Restarts via `POST /api/restart` (5 min cooldown) drop all sockets. Agent report.
- HTTP/WS only: no UDP, so no STUN-style NAT traversal from the server. Agent report.

## queue

- Local daemon, 127.0.0.1 HTTP, bearer `health_token`, port file. Push protocol SemVer 1.7.0, 1 MiB payload cap. Agent report.
- `out-of-scope.md` forbids cross-machine routing and daemon-to-daemon (verified).

- queue-owner answers (2026-11-13; reserved `queue.` prefix, ignored `origin` in requests and "relay events are no more privileged than a local push" verified in `docs/push-protocol.md` and `threat-model.md`; the rest is the owner's reading):
  - No origin field in `push`; an `origin` in a request body is ignored by design. A new field = additive MINOR bump decided by the user. Origin must live in the event name: `machine.<name>.<event>` is accepted (segments `[A-Za-z0-9_-]+`, max 128 chars).
  - Remote wait: recommended design = machine receives peer events and pushes them locally under `machine.<name>.<event>`; local `queue wait machine.<name>.<event>` then works unchanged. Forwarding a long-lived `queue wait` keeps no local history.
  - No origin-based refusal exists in `subscribers.yml`; subscribers on `>` or `*` will also fire on peer events. Peer events are a new, weaker trust level: they need their own threat entry on machine's side.

### queue plugin mechanisms (deep re-analysis, 2026-11-13; items marked [V] re-verified by me)

- Two contracts, neither can add CLI commands or flags:
  - `RelayPlugin` (inbound Source): `{source, mapEvent(envelope)->{event,payload}|null, summarize?}`, `queue-relay-client/src/plugin-api.ts`. Loaded by `loadPlugin(moduleName)`: built-in map first, else a bare `import(moduleName)` [V line 129], error text "use an absolute path or install the package next to the queue CLI" [V line 145]. Configured in `relay.yml` `plugins[{module, subscriptions[]}]`. Loaded on each reconnect. The relay daemon is an esbuild bundle with github/gitlab plugins built in; the review plan flagged that external plugins cannot load in a published install (decision D3 listed open, resolution not confirmed).
  - `ActionPlugin` (outbound, `subscribers.yml` `type: action`): `validate`, `emits?`, `run(config, envelope, ctx)`, `ctx.push` is the only way back to the daemon (`queue-core/src/actions/ActionPlugin.ts`). Registration is BUILT-IN ONLY: `BUILTIN_ACTION_PLUGINS = [agentWakeAction]` [V `builtinActions.ts:5`]; no loader, directory or config key exists, although docs say "install the plugin that provides X".
- Commands are a fixed `switch` (`dlq`, `relay`, `cli`, `sub`, `wait`, `waiters`, `events`) [V `QueueIndex.ts:244-257`]: no plugin-registered commands.
- `subscribers.yml` `type:` values: `cli | http | action`.
- Boundaries: queue and queue-sdk out-of-scope files exclude remote daemons, TLS, other hosts, and cross-machine routing.
- Candidate seams for a remote wrapper (agent list, not a recommendation): a `RelayPlugin` Source whose relay is the machine channel (constraints: `relayUrl` must be `wss://`; `queue wait ci` is hard-wired to `on.github.workflow_run`); a new action type (needs a code change in `builtinActions.ts`); the SDK push protocol locating the daemon through `QUEUE_CONFIG_DIR`; the `QueueClient` (`DaemonClient<QueueCommands>` from singleton-daemon-kit, whether its transport is replaceable is unverified); wrapping the `queue` binary and its stable exit codes.

### task plugin mechanisms (deep re-analysis, 2026-11-13; [V] = re-verified by me)

- Real plugin system with two kinds, `strategy` and `transport` (`task-service/src/plugins/kinds.ts`). Contract `Plugin {extensionPoint, validate (pure, never throws), create(options, ctx), describe}` (`plugin-host/Plugin.ts`); registry instance with refs `plugins.<id>.<impl>` (`PluginRegistry.ts`); slot resolved from the project's `config.yml` `strategy: {type, options}` and `strategy.options.transport: {type, options}`.

- orch-owner answers (2026-11-13; `ALLOWED_ROUTES` exists in `app-module-orchestrator/src/backend/routes.ts`, rest is the owner's reading):
  - A separate local client calling orch's loopback API leaves orch's binding unchanged: compatible with its scope; remote access to the dashboard itself is the scope change.
  - No stable API promise. Closest reviewed surface = the app-core module `ALLOWED_ROUTES` (same as the daemon routes minus secrets, exec, import/export, events).   - `/api/exec` (accepted risk T-05) is accepted only because any local process already runs commands as the same user; a remote peer breaks that premise. orch has no auth, rate limit or caller identity. Recommendation: machine forwards only an allowlist of routes (never exec, secrets, import, job create/update, `/api/open`) with per-peer authorization in the machine daemon.

  - `hooks.json` [V `daemonConfig.ts:96-100`, `help-text.ts:259`]: `cli` or `http` hooks, only `onJobRetry` and `onJobExhausted`; a missing or unparseable file is silently ignored (only one help line documents it).

  - Candidate seams (agent list, not a recommendation): wrapping the `orch` CLI from outside; `orch exec` and the `createDaemonClient` RPC (`cli.ts:2343`); a separate `app-module-machine` contributing to slots (orch's manifest exposes none today); `hooks.json`.

## dsl-owner answers on the passphrase component (2026-11-14, from dsl-view code read-only; not re-read by me)

Console logs carry messages, action names and brain ids (`useActionHandlers.ts:145`, `useBrains.ts:433`); not verified that none echoes a request body or error message with a value.
