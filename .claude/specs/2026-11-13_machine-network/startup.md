# Startup registration with orch

**Version:** v0.2 (2026-11-14). Contract frozen with orch-owner; `orch ensure` and `orch remove --if-exists` are released. Implements decision 3 (orch `startup` job) without a manual `orch add`.

## Contract (orch side, released)

- `orch ensure startup <id> --command "<shell string>" [any add flag] [--restart-if-changed] [--json]`: missing -> add; identical -> no-op; different -> edit. stdout `added|updated|unchanged <id>` (JSON with `--json`). Exit 0 for the three, 1 error, 2 daemon cannot start, 4 usage. Only the flags passed are compared; fields edited by hand and not passed are left alone.
- `orch remove <id> --if-exists`: exit 0 whether it existed; stdout `removed|absent <id>`.
- `--command` is a shell string (cmd.exe on Windows, sh elsewhere): the executable path must be quoted by the caller (`"C:\path with space\machine.exe" daemon`, `'/path with space/machine' daemon`). The stored string is compared exactly, so a moved path counts as `updated`.
- Liveness flags are those of `add`: `--liveness-strategy portFile --liveness-port-file <path>`. The file is JSON with a numeric `pid`; a live pid skips the start (audited). Whether a restart-on-exit restart goes through the same check is not yet verified by orch-owner.
- `orch install` is idempotent (start of the orch daemon at login, user level, no admin). A CLI must not call it by itself: it changes login behaviour for all of orch.

## Machine side (implemented, todo #18)

- Commands: `machine startup enable | disable | status` (status shows whether the orch job exists, its command and whether it is up to date; exit 0 either way, never silent).

- `machine startup enable`: checks that `orch` exists (spawn error -> "orch is not installed: npm i -g @wadeck-app/orchestrator-cli"), then `orch ensure startup machine --command "<quoted exe> daemon" --restart-on-exit --timeout 0 --restart-if-changed --liveness-strategy portFile --liveness-port-file <configDir>/daemon.port.json --json`. If orch's own login entry is missing it prints `run: orch install` and does not run it.
- `machine startup disable`: after the ownership check, `orch kill machine` (ends the running tree; "is not running" is fine, any other failure aborts with the job kept and says so), then `orch remove machine --if-exists`. `remove` alone leaves the running instance alive (decision 63). Output: `[ok] running daemon stopped, startup job "machine" removed` (`stopped: true` in `--json`), or the same without the first part. A manual kill is not restarted by `restartOnExit`.
- Restart rule: a changed command or a post-update uses `orch ensure --restart-if-changed` (orch `restart-job`, honours liveness). Never `orch trigger machine`: it skips the liveness check and starts a second instance. Nothing in machine runs or advises it.
- `machine join` and `machine setup` never enable the startup job by itself: at its end it prints the suggestion `machine startup enable`; with `--auto-startup` it runs `startup enable` as its last step (user decision 2026-11-14). The updater calls `startup enable` after each update only when the job already exists (WP9); the updater calls it after each update (WP9). Exit codes of orch are mapped to actionable messages, never silent.
- The daemon writes the port file (JSON with its `pid`) only while it runs and removes it at exit; a stale file would make orch skip the start.
- Implementation: `startup.ts` (library, orch injectable for tests only; no `--orch` option), `cliStartup.ts`. With the platform launcher package installed the command is the STAGED launcher (`"<configDir>/bin/<stamp>/machine[.exe]" daemon`, Unix prefixed by `LAUNCHER_BUNDLE_OVERRIDE='<bundle>'`; see packaging.md 9.2); from a checkout or the dev bundle it is the development form `"<node>" "<bundle>" daemon`, and `enable` and `status` say which and gets `--config-dir <dir>` when the configuration folder is not the default (orch's environment is not the user's). Started from sources (not a .cjs/.js bundle) it refuses and says `npm run bundle`. On Windows, when the launcher cannot find the bundle by itself (bundle not under `<dirname(node)>/node_modules`), the command is `"<SystemRoot>System32wscript.exe" //B //Nologo "<staged>machine-daemon.vbs"`: a generated script sets `LAUNCHER_BUNDLE_OVERRIDE` and runs the launcher hidden and awaited (orch.cmd cannot carry an environment variable); `status` also compares the script (packaging.md 9.2a).
- Windows node_modules junction (`bundleLink.ts`): in that same case, when the bundle sits at `<node_modules>/@wadeck-app/machine-cli/machine.cjs`, `<configDir>\bin\<stamp>\node_modules` is a directory junction (no admin right) to that `node_modules` folder, so the staged launcher also finds the bundle by itself (its walk up `node_modules`, e.g. global npm in `%APPDATA%\npm`, otherwise "cannot find the bundle"). Created by `enable` before orch is called, re-checked and repaired (missing, stale, dangling) by `status` and, through `enable`, by post-update; reported as `[ok] bundle link ...` or `[warn] bundle link: <cause>, <fix>` (a failure never fails `enable`: the wrapper still carries the job). A real folder of that name is never touched. Removing the staged folder (prune) removes only the junction. Port of orch `bundle-link.ts`.
- Wrapper form command: `wscript.exe //B //Nologo "<vbs>" <hash>`; `<hash>` = first 12 hex of sha256 of the script content, ignored by the script. A moved bundle changes the script, hence the command, hence `--restart-if-changed` restarts the daemon (chosen over a hash in the file name: the staged path, pruning and `status` stay unchanged). Jobs registered before this change lack the hash and read as outdated once.
- `disable` runs `orch show` first and removes only a job it owns: command of a form machine writes (ending in `daemon [--config-dir ..]`, or the wrapper) AND `liveness.portFile` = this configuration's port file. Otherwise it refuses (exit 1) with the command found and `orch remove <id>` as the manual fix. No ownership marker: orch has no owner field and a job matching both tests is the same daemon.
- `status` also runs `orch list --json` and lists any other job whose `liveness.portFile` is this port file (`conflicts` in `--json`); the CLI prints `[warning] ... orch remove <id>` on stderr, exit stays 0. An unreadable `list` answer fails loudly. Not verified against the real orch: the `liveness.portFile` and `list --json` shapes are read from orch's sources (`types.ts`, `cli.ts`), not from a run.
- On Windows `orch.cmd` runs through cmd.exe; a path or argument containing `& | < > ^ %` is refused loudly.
- Not in the frozen contract, accepted tolerantly: the JSON shape of `ensure`/`remove` (any string field equal to the outcome word) and of `show` (`command` at top level or under `job`). Not verified against the real orch.
- `machine join --auto-startup`: runs enable after a successful join; a failure is reported and join exits 1 (the join is kept).
- Port file: `<configDir>/daemon.port.json` = `{pid, port, peerPort}`, mode 0600, written last (listeners up), removed on stop, signals and process exit only if it still names this pid.
- Bundle: `npm run bundle` writes `dist/machine.cjs` (git-ignored); `npm run bundle:all` also writes `machine-updater.cjs` and `app-module/` (packaging.md 9.5-9.7).
- Update records in `<configDir>` (written by the updater, packaging.md 9.5): `update-blocked.json` (failed target, retried after 24 h in the background), `post-update-pending.json` (installed but post-update failed, retried by the next updater run), `update-notice-seen.json` (terminal notice already shown), `update-starts.json` (loop guard, daemon). A corrupt record is reported with "delete it"; none holds a secret.

## Verified against the real orch (2026-11-14, orch 2026.11.14-592)

A throwaway job (library-only options `id` and `restartOnExit`, default `machine` and true) was ensured with a command holding three quoted segments with spaces and, in a second run, parentheses: stored byte for byte, then `unchanged`, `updated`, `removed`; the job list was identical afterwards. The real `machine` job has not been registered on this machine yet.
