## Executive summary

The root of trust is weaker than the threat model admits. The admin key is copied on every machine and unlocked by a passphrase typed in a shared browser origin; the acceptance of AR-2 contradicts P-5 and T-11. The enrollment safeguard (35a) is grindable by a hostile relay. Revoking a stolen machine does not neutralize the admin key copy it carries. Several protocol claims cannot hold as written: a listener that reveals nothing before authentication, a PSK that protects when the identity key leaks, and freshness of revocations and signed policies.

## Findings

| ID | Severity | Finding | File / Section | Recommendation |
|---|---|---|---|---|
| S-01 | CRITICAL | AR-2, T-13 and T-14 accept that another module captures the passphrase because a module "already has the user's OS rights". Incomplete: the admin key signs for ALL machines, so a trojan module on the desktop gains signing power over the work laptop, which its OS rights do not give it. A same-user process can register a module through app-core's unauthenticated `/api/modules/register` (T-03); with the readable encrypted key file (decision 23) a prompt-injected agent can widen every machine's policy. Contradicts P-5 and AR-1's own clause. | AR-1, AR-2, T-11, T-13, T-14; decisions 19, 23; P-5 | Reword AR-2 (loss is network-wide admin, not local rights). Move passphrase entry out of the shared origin (CLI prompt as primary, or D-H option A) or get an explicit user re-confirmation; pin the module bundle hash and have the daemon refuse signatures from an unpinned module. |
| S-02 | CRITICAL | Safeguard 35a is grindable: if the random value travels in clear next to the candidate key, the relay generates its own key and random until the short code matches, then swaps the candidacy; the final code is a function of both public keys, so the relay grinds fake admin keypairs. A 6-digit code costs about 10^6 keypairs (seconds). Code length is still "to be fixed". T-05 is marked Planned although the relay MITM is not stopped. | decision 35a; T-05; WP1, WP7 | Commit-then-reveal SAS, or a code of at least 64 bits compared as words or a hash prefix; state the attacker compute budget; add a test that grinds the code and asserts failure. |
| S-03 | CRITICAL | T-06 says revocation handles a stolen machine, but that machine holds an encrypted admin key copy (decision 23). Revoking its UUID does not touch the blob: the thief guesses the passphrase offline, then signs registrations, PSKs and policies for the whole network. Only full re-initialization (decision 26) closes this. No minimum passphrase entropy is enforced; changing the passphrase later does not invalidate stolen blobs. | T-06, T-22, AR-7; decisions 23, 26 | State in T-06 that losing a machine means rotating the admin key unless the passphrase has high entropy; generate the passphrase at init (at least 80 bits) and refuse weak ones; document the stolen-machine runbook before enrolling the work laptop. |
| S-04 | CRITICAL | The unlock window (decision 18) signs anything while open, with no per-change confirmation. The page DOM is drivable and the actor table lists an agent that "can drive a browser": an agent can open the Policy page during the window and add an entry. Contradicts P-5 and T-11 for an in-scope actor. | decision 18; T-11; actors | Require the passphrase (or a challenge shown only on the local CLI) per widening signature, or render a what-you-sign summary from the canonical bytes with a non-click-only confirmation; hard maximum for the window; zeroize on tab hide or close. |
| S-05 | CRITICAL | A hostile relay (A-1) still reaches command execution on the same machines through queue: queue trusts relay events ("trust transfer"), its forged-webhook threat stays Open, and its `cli` and agent-wake subscribers run commands as the user. This bypasses machine's allowlist, signed policy and E2E channel. Listed only as phase 2 (T-09). | A-1; decision 5; T-09; evidence queue section | Add a phase 1 threat "relay-originated command execution through queue subscribers on enrolled machines"; forbid relay-fed `cli` and `action` subscribers on enrolled machines or accept it in an explicit AR. |
| S-06 | HIGH | The Noise variant is open (XXpsk3 or IKpsk2) and neither honours T-34: in XX the responder sends its static key and registration in message 2 before the PSK is checked; in IK anyone who knows the responder's public key (published on the relay) gets a reply; both force signature verification before authentication (CPU amplification); a TCP accept then silent close is distinguishable from a closed port. | T-34; hard rule 1; T-35; D-B | Use a pattern that mixes the PSK in message 1 so a wrong first message is dropped; no application data in message 1; reword T-34 to "scanners learn the port is open, nothing else"; add a conformance test. |
| S-07 | HIGH | The claim "leak of the identity key alone is not enough, the PSK is missing" is false against the stated adversary: PSKs travel through the relay sealed to each machine's identity key, and the retaining relay holds those blobs. Identity-key theft plus relay data yields every PSK of that machine. | decision 22; D-B addendum; T-22; T-35 | Seal with an ephemeral-static scheme, deliver once, delete on ack; otherwise drop the claim; add PSK versioning. |
| S-08 | HIGH | Revocation has no freshness guarantee: a hostile relay or stale peer can withhold the new list; the handshake does not exchange list or policy versions; `validTo` has no maximum or renewal rule; decision 25 says "versioned list", decision 27 says "grow-only set"; propagation is unspecified. | decisions 24, 25, 27; T-06; T-20 | Exchange the revocation version in the handshake and refuse a peer claiming a lower one; short maximum `validTo` with renewal; choose the grow-only set and specify propagation. |
| S-09 | HIGH | Signed policies have no validity window: a widening policy signed at base N but never applied stays valid forever for a target at N; a wipe or restored backup resets the version and revives old policies; delivery path unspecified; hard rule 4 ("higher version") differs from decision 27 ("base equals current"). | decision 27; T-16; hard rule 4 | Add notBefore, notAfter and a nonce; store the highest seen version outside the editable store anchored with the audit chain; specify delivery with an ack; align hard rule 4. |
| S-10 | HIGH | AR-9 (no signature or provenance on updates, auto-update every 30 minutes) is accepted, yet WP10 enrolls the work laptop; a poisoned release also replaces the admin page bundle (same package), capturing the passphrase and signing: network-wide admin, not just RCE as the user; no downgrade protection. | T-23; AR-9; decision 38a; plan WP9, WP10; rule 10 | Make npm provenance verification (or a signature pinned in the binary) a WP9 precondition; `autoUpdate: false` on the laptop; refuse older versions without an explicit command. |
| S-11 | HIGH | The browser KDF is an unvalidated assumption: under `script-src 'self'` without `wasm-unsafe-eval` WebAssembly argon2 will not load and WebCrypto offers only PBKDF2; the same key file must decrypt in the Node CLI (decision 36); no spike planned. (Confirmed since by app-core-owner, see evidence.md.) | T-13; AR-7; decisions 18, 36; WP1, WP8 | Early spike for KDF and parameters under the CSP; explicit parameters and format version in the key file; CLI-to-browser cross-decrypt test. |
| S-12 | HIGH | T-17 covers only peer-to-local. In the local-to-remote direction any local process holding the daemon's `health_token` can call `machine run` and use the machine's grants on every peer; output flows into agent context and possibly to a model provider. | T-17; T-28; AR-6; decisions 13, 14 | Add a caller-side threat; options: a human-configured capability for calling peer X, a per-run grant, or an explicit AR. |
| S-13 | HIGH | Legacy tokens stay full access (decision 29): the queue token stored in plaintext on every machine keeps control-plane rights until rotated; a stolen one can mint a `machine` token, read presence and addresses and post candidacies; T-30 and T-31 rely on scoping, which protects nothing while an unscoped token exists. | decisions 29, 30; T-30, T-31, T-32; AR-8 | Make rotating all existing tokens to scoped ones a precondition for enabling the `machine` routes; have the daemon refuse to start the relay client if `whoami` shows an unscoped token. |
| S-14 | MEDIUM | A registered but malicious peer can publish a validly signed address record pointing to any host and port (intranet service, metadata endpoint): SSRF and port-scan oracle from the caller's network position. T-33 covers only the relay lying. | T-33; decision 34 | Reject loopback, link-local and metadata ranges, enforce a configured port range, connect timeout and per-peer rate limit, log address changes. |
| S-15 | MEDIUM | Output of a remote command is untrusted data from a possibly compromised target (terminal escapes, prompt-injection text into the caller and the agent). | T-19; T-28; rule 9 | Strip or escape control characters on a TTY, mark remote output untrusted in `--json`, add a "malicious target to caller" threat. |
| S-16 | MEDIUM | An exact string match does not pin what runs: `ls`, `ipconfig` and `ps` resolve via PATH and, in cmd, the current directory; cwd and PATH are unspecified; a planted binary or `.bat` runs under an approved entry. | T-15; T-18; decisions 13, 17; evidence | Fix the cwd to a protected directory, define PATH, pin the resolved absolute path (and hash if feasible) in the signed entry, add a planted-binary conformance test. |
| S-17 | MEDIUM | Pending requests let a peer choose the strings the human is asked to approve: fatigue and lookalike strings make this a social-engineering channel; T-21 treats only spam. | D-G; decision 20; T-15; T-21 | Display exact escaped bytes; forbid "always" directly from a pending request; cap length and character set before display. |
| S-18 | MEDIUM | Rotation (decision 26) accepts a rotation record signed by the old key, so a compromised old key can rotate the network to the attacker's key; no epoch or cut-over. | decision 26; AR-7 | Add an admin key epoch to every signed document, pin the highest seen, treat a possibly compromised key as re-initialize only. |
| S-19 | MEDIUM | Time handling contradicts A-5 and T-26: registrations carry `validFrom` and `validTo`, requests carry an expiry, but T-26 says "counters, not clocks"; a stolen machine can set its clock back; the verifying clock is unspecified. | decision 24; T-26; T-29; A-5 | State the verifying clock and tolerated skew per document type; fail loudly with the measured skew. |
| S-20 | MEDIUM | Crypto choices unvalidated: no vetted Noise library for Node identified; one seed deriving both curves risks cross-protocol key reuse; WP1 has no handshake known-answer tests. | D-B; WP1, WP5; T-35 | Library-selection and review spike in WP1; domain-separated derivation; Noise test vectors. |

| S-22 | MEDIUM | Candidate-controlled fields (UUID, name, computer name) get signed after a visual check and then drive references; nothing says what happens if a candidate presents an existing UUID (silent key replacement via a higher serial) or a lookalike name; the key of the per-peer policy is not stated. | decisions 10, 11, 24, 35; T-05 | Treat a UUID or name collision as a blocking case; generate the UUID admin-side or derive it from the key; policies keyed by UUID. |

## New open questions raised

- Which SAS construction and code length for enrollment, and what attacker compute budget (S-02)?
- Which minimum passphrase entropy; is "any lost or stolen machine means network re-initialization" accepted for the work laptop (S-03)?
- Per-change confirmation or passphrase instead of a time window (S-04)?
- Do queue relay subscribers bypass machine's allowlist, or must they be disabled on enrolled machines (S-05)?
- Which Noise pattern (PSK in message 1) and which library; what may an unauthenticated scanner learn (S-06, S-20)?
- How are revocations, policies and PSK records delivered, and how does a peer discover it is behind (S-07, S-08, S-09)?
- Which KDF and parameters run in the app-core page under the CSP (S-11)?
- May a local process or agent call `machine run` unprompted, and who authorizes the caller side (S-12)?
- How are existing relay tokens rotated before the `machine` scope is enabled (S-13)?
- Are provenance or signature checks a precondition of the first release that enrolls the work laptop (S-10)?
- What restricts and what releases a lockdown, and over which channel (S-21)?
