## 1. System and data flow

```
 caller (human or agent, same OS user)
        | loopback API + health_token            TB-1
        v
 +----------------+  HTTPS REST (auth, `machines`)  +-----------------+  HTTPS REST   +----------------+
 | machine daemon | ==============================> |  relay (poc-node) | <============ | machine daemon |
 |  (caller)      |  TB-2: registry only, UNTRUSTED  |  never carries    |  TB-2         |  (target)      |
 +----------------+                                  |  commands         |               +----------------+
        |                                            +-----------------+                  ^   | TB-4
        |   direct TCP connection to the published address (TB-3)                         |   v
        +---------------- mutual handshake, E2E-encrypted, signed requests ---------------+  allowlisted
                                                                                              shell command
 admin page (app-module-machine, app-core origin)  --signed policy (TB-5)-->  target daemon
```

| Boundary | Between | Control (summary) |
|---|---|---|
| TB-1 | Local caller and the local daemon | Loopback only, bearer `health_token` (same as siblings). NOT proof of a human (P-5) |
| TB-2 | Daemon and relay | Outbound HTTPS only (authentication, REST resource `machines`); the relay is untrusted, never carries commands, and is never believed about identities: a registration counts only with the admin signature |
| TB-3 | Peer and peer | A direct connection to a listening peer port (decision 34); mutual authentication before anything else, allowlist of enrolled UUIDs, session keys, request signing. This is the machine's only network-reachable surface |
| TB-4 | Daemon and the executed command | Exact-match allowlist, scrubbed env, timeout and output cap, never elevated |
| TB-5 | Admin page and daemon | Policy changes accepted only with a valid admin signature |

## 2. Assumptions

| # | Assumption | Basis |
|---|---|---|
| A-1 | The relay (poc-node, shared hosting, one process) is hostile or breached at any time | decision 5; poc-node: "no roles by design", a stolen token "grants everything" [V `docs/THREAT_MODEL.md:57`] |
| A-2 | Any process running as the same OS user on a machine can read daemon tokens and edit user files, including an agent session | [V] `health_token` files are readable by this agent session; [V] queue: "the file system is the trust boundary" |
| A-3 | Such a process already has the user's rights on THAT machine; the policy protects a machine against REMOTE peers and against agents widening the remote surface, not against malware already running as the user | P-5 scope; decision 19 |
| A-4 | Enrollment of a machine is a human act on both sides | decision 6; open question #4 |
| A-5 | Machine clocks may be skewed; expiry and replay logic must not trust a peer's clock alone | (inference) |
| A-6 | On Windows, file modes are not enforced; the user profile ACL is the boundary | [V] queue threat model line 43; flow AR-8 [agent] |
| A-7 | The user's own app-core modules are trusted; a malicious module already has the user's OS rights | decision 19 |

## 3. Assets

| Asset | Sensitivity | Where |
|---|---|---|
| Ability to run commands on a machine | Critical | target daemon |
| Admin signing key (encrypted) and passphrase | Critical | admin key file; passphrase in the human's head |
| Machine identity private key | Critical | `<configDir>/_secrets_` |
| Policy: allowlists, per-peer lists, grants, limits | High | signed policy file on each machine |
| Peer registry (UUIDs, public keys, aliases, PSKs) | High | machine config |
| Audit log | High | hash-chained file on each machine |
| Command output in transit | High | peer channel (E2E) |
| Relay credentials | Medium | machine config |
| Traffic metadata (who, when, sizes) | Low | visible to the relay |
| Work laptop and its corporate data | High | the laptop |

## 4. Actors

| Actor | Motivation | Capability | In scope |
|---|---|---|---|
| Internet attacker | Reach machines | Can connect to the public relay URL, pre-authentication | Yes |
| Compromised relay or relay host operator | Pivot, spy, deny | Full control of relay data, sockets and restarts | Yes (assumption A-1); host operator attacks on the hosting are out of scope as in poc-node |
| Stolen or lost machine | Pivot to the network | Holds an identity key, peer registry, audit log | Yes |
| Compromised enrolled peer | Execute on others | Valid identity and PSK | Yes |
| Prompt-injected or confused local agent | Follow injected instructions | Same OS user: reads tokens, edits files, can drive a browser | Yes (policy and admin) |
| Malware running as the user | Anything | The user's full OS rights | Out of scope beyond what A-3 states |
| Malicious app-core module | Capture passphrase | Shell-origin DOM access | Accepted (AR-2) |
| Malicious or buggy sibling release | Deploy hostile code | Auto-update path (orch updates every 30 min [agent]) | Partly (T-23) |

## 5. STRIDE analysis

**Spoofing.** A peer or the relay impersonating a machine (T-01); a stolen relay token (T-30); a rogue machine enrolled (T-05); a local agent acting as the human administrator (T-11); a trojan admin page (T-14); a signed request redirected to another target (T-29).
**Tampering.** Frame modification and replay on the direct channel (T-02, T-04, T-35); address poisoning (T-33); policy tampering or rollback (T-16); command-string bypass of the exact match (T-15); counters reset locally (T-12).
**Repudiation.** No trace of remote commands: a known gap of the daemon kit (T-07); audit log truncation by a same-user process (T-27).
**Information disclosure.** Metadata seen by the relay (T-25); key theft (T-22); passphrase capture (T-13); environment leaking into commands (T-18); output exfiltration through allowed commands (T-28).
**Denial of service.** Pre-authentication flood on the relay routes and the peer listener (T-08, T-34); relay outage or dropped connection (T-20); pending-request spam (T-21); command resource exhaustion (T-19); administrator lockout (T-24); clock skew (T-26).
**Elevation of privilege.** Compromised peer (T-03); scope escalation on the relay (T-31, T-32); local agent widening policy (T-11); confused deputy through the local token (T-17); self-update channel (T-23); phase 2 forwarding (T-09, T-10).

It cannot manage tokens, so it cannot mint further tokens. Detect: unexpected candidacy decisions or `not_owner` on a machine. Fix: revoke the token in the relay console, then `machine admin login --force` (and `machine join --resume` where a uuid was rebound) | The user asked for one confirmation and no second login (decision 59); the alternative (full access) is worse, and a separate admin token on the first machine only splits the file, since its daemon runs as the same user | A relay offers a scope without the inbox and machine deletion rights; the daemon of the admin machine is isolated from the admin token |

**Ping (decision 61).** `machine ping <machine>` is the first half of a `run` (the mutual TLS handshake and the revocation `hello`) with no request after it. A registered peer could already do that, so no right is added. It is not read-only: the hello is the real catch-up, so the caller may install the admin-signed revocation lists the peer hands over and records the peer's announced version (local files; the lists only restrict), and sends its own lists when the digests differ. What the target sees: nothing in its audit log when the hello is answered (`revocation.seen` updates its local record of the caller's revocation version; it verifies and merges received admin-signed lists, which only restrict); an older build audits one `refused unknown-message`; the per-peer limit of 6 revocation exchanges per minute per caller is audited once a minute when exceeded; that budget is shared with `run`, and `--count` stays under it (hello in the first 4 rounds only). A refused hello is shown as "not compared", never as a difference of the lists. Up to 10 connections one second apart count against T-34 like any registered peer's. The relay form sends only `GET /api/version`, `GET /api/whoami` and the machine's own record read: no new call.

**Wake-on-LAN, phase A (decision 62).** `machine run`, `machine ping` and `machine wake` can send magic packets from the CALLER when a peer cannot be reached. Hard rule 3 is untouched: nothing goes to the peer, no request type or wire field is added, the daemon is not involved; hard rule 1 too (UDP is only sent, never received, no new listener). Hard rule 5: the relay chooses neither the MAC (typed by the user), nor the method, nor whether to wake. Phase B (a machine sending the packet for a caller outside the LAN) is a capability that makes ANOTHER machine act: it needs the hard rule 3 amendment and its own rows (connectivity.md 4.5), and is not built.

| Question | Answer |
|---|---|
| What a packet does | 102 bytes of UDP (port 9): the NIC of the target matching its MAC powers the machine on. It grants no access: the connection still needs the pinned TLS key, the pair secret and an allowlist entry |
| What it reveals | It is cleartext: whoever is on the LAN sees a wake of this MAC at this time from this address. A mistyped MAC wakes another device (harmless) |
| Who triggers it | The local user: the settings are local files (`connections.json`, no secret). A same-user process (A-2, A-3) can edit them and make the next `run` or `ping` send packets, but it can already run anything as the user; it gains no right on a peer |
| Where a packet may go | Only (1) a known IPv4 address of the peer inside a subnet this machine is on and (2) that subnet's directed broadcast, UDP port 9, bound to that interface. Never 255.255.255.255, never an address outside the LAN, no blind broadcast when the machine is not on the LAN (explicit error). A name or an IPv6 address is never unicast to |
| What makes it fire | Only a connection failure that is `unreachable` or `timeout` for EVERY address (a type, not a message match). Authentication, registration, revocation, pin, pair-proof, protocol and DNS failures never wake |
| Abuse limits | At most 8 packets per method per invocation (defaults 4 each), a wait of at most 600 s, a cooldown of 60 s per peer between two wake runs (`wake-state.json`: a same-user reset is accepted, AR-5), one wake per `ping` |

Residual with NO pinned address: it can replay an old, validly signed record of the peer (T-33), which can aim the unicast at an address that now belongs to another host of the caller's subnet (102 bytes to UDP 9); it can also make connections time out to trigger wakes, within the limits above. Pinning an address removes the first |
| Trace | `wake-audit.log` on the caller: hash-chained (T-07 format), one entry per packet written BEFORE the send (who, peer, MAC, method, n of total, destinations) and one result; "sent", never "woke". An unwritable or edited log means no packet. The MAC and the addresses are not secrets |
| Not covered | A stolen peer can still be woken by anyone on its LAN: revocation does not stop a NIC from listening (it is still protected by TLS pinning, the pair secret and the allowlist). The daemon starts at login (decision 3): a machine woken from power-off without auto-login does not listen, so the target must sleep, not shut down |

No `Open` threat ships with it (hard rule 10).

**Deny from another machine (not built).** Only the admin may deny a request held elsewhere, with the same signed frame gate as `requests-list`; a registered requester or any other peer may not (a peer could otherwise refuse the callers of others). Until that frame exists, the owner denies on the target.

**Deny button (hold-for-approval.md).** A Deny restricts (answers a waiting caller `refused: denied`), so it needs no signature (hard rule 4). The web route `POST /deny` is nevertheless `sensitive` (app-core PIN, same as the Allow routes): a local process that merely reaches the app-core port cannot deny the owner's held requests (denial of service on a caller, with a reason text the agent reads). `machine requests --deny` is unprotected on purpose: it needs the local daemon token, i.e. the local user at the terminal. The reason is printable ASCII, 200 characters, and is shown to the caller and kept in the audit log.

**Allow button: passphrase in the shared origin (decision 76, T-13, T-14, T-39).** The Requests page now asks the admin passphrase and signs in the browser, so T-13 and T-14 are live for this action (accepted AR-2, unchanged).

| Question | Answer |
|---|---|
| Where the secrets are | Passphrase: the input field, read once at submit and cleared, then used for one signature. Key: a non-extractable `CryptoKey`, locked before the post. Never in a request body, URL, storage, log or error (tests grep all of them). Not remembered |
| What the backend serves | The ENCRYPTED admin key file (route `sensitive`, refused unless the file is an encrypted envelope with only the known fields). Its clear `hint` (decision 57) is readable by anyone who can reach the route, as by anyone who reads the file (AR-7). New exposure: any script of the shared origin that holds the app-core PIN session can fetch the encrypted file and guess offline, as a same-user process already can |
| What the backend accepts | Exactly `{ policy, document? }`, both signed documents; any other field is a 400 (a passphrase cannot be forwarded). The daemon re-verifies the admin signature against the pinned key, the target (this machine or a trusted peer), mode (admin only) and the base version (compare-and-set), then stores like the CLI. | Hostile backend and the base | The page computes the next body itself (`nextPolicyBody` copy, proven equal to machine-core) from a base whose signature it verifies against the pinned key: a backend cannot slip entries into what the admin signs. **Passphrase hint (decision 57).** The optional hint is stored in CLEAR in the admin key file and shown at every unlock prompt, so anyone who reads the file (same-user process, stolen machine, a copy of the key) reads the hint without the passphrase. It must never contain the passphrase: the tool refuses a hint that contains it (case-insensitive) but cannot judge a hint that merely makes it guessable, which lowers the cost of the offline guessing already accepted in AR-7. The hint is authenticated (part of the AEAD header), but it is shown BEFORE the passphrase is typed, so a swap is not prevented at that point: it is detected when the file is decrypted (the unlock fails like a wrong passphrase), after the person already read the misleading hint. A swap can therefore mislead one prompt, never the key itself; whoever can swap it can also delete the file. 80 printable ASCII characters only, so no control sequence reaches the terminal.

**Security code on the joining machine (decision 67, T-05).** `finalCode(candidate key, admin key, random)` (SHA-256 over both public keys and the candidacy random, `machine-core/sas.ts`) is computed twice: by the admin machine from its own key, by the candidate from the admin key carried by the approval. At its first join the candidate has no pinned admin key and no secret shared with the admin: `checkApproval` verifies every registration against the admin key found IN the approval. The relay reads the candidacy (key, name, uuid, random) and can answer with an approval signed by its own key, registrations and sealed pair secrets included (anyone can seal to the candidate key, T-36); every check of the candidate passes. Only the final code differs from the one the real admin machine shows.

- Consequence 1: any confirmation the admin sends through the relay is forgeable by it, because the candidate has nothing to authenticate it with. The comparison is a human act over a channel the relay does not control.
- Consequence 2: the pin decision is taken where the pin happens (the joining machine, `applyApproval`). A decision on the admin side alone cannot stop a pin the relay induced.
- `--yes-final-code` makes the machine compare the typed code with its own (mistyped or substituted code: no pin) but cannot know the origin of the typed text; a code copied from a message that crossed the relay is as forgeable as a `y`.
- A `y` without reading pins the relay's admin key: by hard rule 4 that key signs the policies and registrations this machine accepts, so the relay becomes the administrator of this machine. Not mitigated by anything else on the candidate; accepted as the one human step (decision 50).
- Future option, NOT implemented and NOT verified: bind the code to a secret that both machines know before the approval, such as the relay login code. The relay itself issues that code (device login returns it to the CLI, the pairing code comes from the relay console), so whether it is a secret against the relay is part of what such a change would have to establish. It would change this threat model (a new pre-shared secret, its lifetime and its leakage); until then the comparison above stays the control.

## 8. Hard rules (must not change without revisiting this model)

1. The machine daemon opens exactly two listeners: the loopback API (TB-1) and one peer listener (TB-3, decision 34), on separate servers and ports. The peer listener answers nothing before a valid first handshake message, parses nothing else pre-authentication, and is never reached by the local API. (Replaces the earlier rule "no listening port other than loopback", voided by decisions 33-34.)
2. The local loopback API and the peer channel are separate code paths; a local token never authorizes a peer request.
3. A peer request is executed only if it matches an allowlist entry for that peer, within its limits: byte for byte for an exact entry, or, for a typed entry signed under rule 4 (decision 79, amendment to confirm by the user), with every fixed word equal and every value accepted by the whitelist of its type; no wildcard, no regex, no free command on the wire.
4. A change that widens rights (policy, registrations, pair secrets) is applied only with a valid signature whose base version equals the current one (compare-and-set, decision 27). Registrations, pair secrets and revocations need the admin signature, always. A policy needs the signature chosen by the mode of the target machine (decision 68, amended by the user 2026-11-20): mode `admin` (default) the admin key; mode `local` the policy key of THAT machine only, for what runs on that machine only. The local key cannot enrol a machine, cannot lift a revocation, and signs in its own domain (`machine/policy-local/v1`), so no signature is valid in both modes. Only restricting actions (cut one pair, lockdown, decision 25) need no signature, and they are logged. A typed entry, a type bound and a lifetime are part of the signed policy (decision 79): widening a bound, adding a type or renewing a limit is a policy change and needs the same signature; the signing summary (template, lifetime, examples) is read BEFORE the passphrase.
5. The relay is never trusted: nothing it sends is acted on unless authenticated end to end; every failure is reported, never swallowed.
6. A non-encrypted or unauthenticated connection is refused (fail closed), not warned.
7. The daemon runs as the user, is never elevated, and never exposes quit or restart over the network.
8. No secret, token, passphrase or key material in logs, errors or the audit log.
   - Run log (decision 82, run-log.md): the outgoing run log stores the command as typed plus names, outcome and times, never environment, passphrase or output; commands must not carry secrets (same rule as the allow list). Its files are 0600 in a 0700 folder under the config directory.
9. Executed commands run with a scrubbed environment, a timeout, an output cap, without interaction.
10. An `Open` threat must not ship inside a feature that depends on it (flow's rule for T-05..T-08 [agent]).
11. No message between machines is readable by the relay (decision 78): every inbox document and every approval is sealed to the identity key of its addressee, with a context naming the type, the addressee and the id. There is no plaintext mode: the builder throws without the key, the client refuses to send a clear document, the receiver refuses and audits one. Only what the relay must use stays readable: address records, candidacies, presence (T-25).
