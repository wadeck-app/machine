# Threat Model -- Machine Network

**Version:** 3.0 (2026-11-14: T-36 pair secrets sealed in the approval; the relay is a registry only and peers connect directly, decisions 33-34; hard rule 1 is replaced, T-33 to T-35 added)
**Date:** 2026-11-14
**Methodology:** STRIDE, format aligned on the sibling models (flow docker-sandbox: Assets/Actors tables + register with Status and Decision #; flow-cli: accepted risks `AR-n` with a re-evaluation trigger; orch: hard rules)
**Scope of this version:** phase 1 (decision 12): machine identity, enrollment, secure channel through the relay, remote command execution under a human-administered allowlist. Phase 2 (wrappers for task, flow, queue, orch, project) is parked; section 9 lists what must be re-evaluated before it ships.

Sources are tagged `[V]` when I re-read the quoted line myself, `[agent]` when it comes from a sub-agent report not re-verified. Inferences are marked "(inference)". See section 11.

## 1. System and data flow

```
 caller (human or agent, same OS user)
        | loopback API + health_token            TB-1
        v
 +----------------+  HTTPS REST (auth, `machines`)  +-----------------+  HTTPS REST   +----------------+
 | machine daemon | ==============================> |  relay (poc-node) | <============ | machine daemon |
 |  (caller)      |  TB-2: registry only, UNTRUSTED  |  never carries    |  TB-2         |  (target)      |
 +----------------+                                  |  commands         |               +----------------+
        |                                            +-----------------+                  ^   | TB-4
        |   direct TCP connection to the published address (TB-3)                         |   v
        +---------------- mutual handshake, E2E-encrypted, signed requests ---------------+  allowlisted
                                                                                              shell command
 admin page (app-module-machine, app-core origin)  --signed policy (TB-5)-->  target daemon
```

| Boundary | Between | Control (summary) |
|---|---|---|
| TB-1 | Local caller and the local daemon | Loopback only, bearer `health_token` (same as siblings). NOT proof of a human (P-5) |
| TB-2 | Daemon and relay | Outbound HTTPS only (authentication, REST resource `machines`); the relay is untrusted, never carries commands, and is never believed about identities: a registration counts only with the admin signature |
| TB-3 | Peer and peer | A direct connection to a listening peer port (decision 34); mutual authentication before anything else, allowlist of enrolled UUIDs, session keys, request signing. This is the machine's only network-reachable surface |
| TB-4 | Daemon and the executed command | Exact-match allowlist, scrubbed env, timeout and output cap, never elevated |
| TB-5 | Admin page and daemon | Policy changes accepted only with a valid admin signature |

| # | Assumption | Basis |
|---|---|---|

| A-6 | On Windows, file modes are not enforced; the user profile ACL is the boundary | [V] queue threat model line 43; flow AR-8 [agent] |
| A-7 | The user's own app-core modules are trusted; a malicious module already has the user's OS rights | decision 19 |

## 5. STRIDE analysis

**Spoofing.** A peer or the relay impersonating a machine (T-01); a stolen relay token (T-30); a rogue machine enrolled (T-05); a local agent acting as the human administrator (T-11); a trojan admin page (T-14); a signed request redirected to another target (T-29).
**Tampering.** Frame modification and replay on the direct channel (T-02, T-04, T-35); address poisoning (T-33); policy tampering or rollback (T-16); command-string bypass of the exact match (T-15); counters reset locally (T-12).
**Repudiation.** No trace of remote commands: a known gap of the daemon kit (T-07); audit log truncation by a same-user process (T-27).
**Information disclosure.** Metadata seen by the relay (T-25); key theft (T-22); passphrase capture (T-13); environment leaking into commands (T-18); output exfiltration through allowed commands (T-28).
**Denial of service.** Pre-authentication flood on the relay routes and the peer listener (T-08, T-34); relay outage or dropped connection (T-20); pending-request spam (T-21); command resource exhaustion (T-19); administrator lockout (T-24); clock skew (T-26).
**Elevation of privilege.** Compromised peer (T-03); scope escalation on the relay (T-31, T-32); local agent widening policy (T-11); confused deputy through the local token (T-17); self-update channel (T-23); phase 2 forwarding (T-09, T-10).

| T-36 | I, S | The relay (or a thief of the admin token) reads the pair secrets carried by an enrollment approval, then combines them with a stolen or swapped identity key to impersonate a peer | Decision 22: each pair secret is sealed to the candidate identity key (`machine-core/seal.ts`: ephemeral X25519, HKDF-SHA256, AES-256-GCM) with a context binding admin uuid, candidate uuid, candidacy random and entry; the relay stores only sealed values; old approvals with a clear `pairSecret` are refused. Residual: sealing does not authenticate the sender (anyone can seal to a public key) and the sealed value is not signed. The sender is authenticated by the admin signature on the registration and by the final code. A relay that replaces a sealed value with its own secret makes the candidate hold a secret the other peer does not have: the first connection fails the channel-bound pair proof (HMAC over the TLS exporter, `machine-transport/src/channel.ts`, error "failed the pair secret proof ... the pair secret differs"), never silently. The relay cannot learn the real secret by this. Sealing is to a long-term key: a later leak of the candidate identity key also exposes a recorded sealed value (that key alone already allows impersonation of that machine). NOT mitigated by sealing: a relay that swaps the candidate public key (the T-05 case) makes the admin seal the pair secret of the admin-to-rogue pair to the RELAY key before the final code is compared (decision 50). The relay then learns that one pair secret and holds a signed registration for its key until the admin runs `machine admin revoke` (same residual as T-05). The first-code comparison, not sealing, is what catches it. The manual file flow (decision 48) still carries the secret in clear in the file the human moves. Distribution documents (distribution.md): the pair secret of two peers is derived deterministically from an HKDF subkey of the admin seed (`machine/pair-secret/v1`) and the two uuids and serials, so a retry or another admin machine seals the same value. Consequence: every pair secret is recomputable by whoever holds the unlocked admin key and the public registrations; pair secrets add no protection against theft of the admin key (which already allows rogue registrations, AR-7), and still protect against a stolen machine identity key alone and against the relay | Mitigated by sealing | 22, 42, 48 |
| T-37 | S, E | Approving a device login without comparing grants an attacker's request: a public `device-login/start` can carry any label, so a distracted approval gives the attacker a `machine` or `machine-admin` token (poc-owner residual) | The relay console shows the real code, label, access chip, source address and age with ONE Approve button; the CLI prints the code and says to compare it and the source address before approving; a stricter relay mode (6 clickable codes) is opt-in. A `machine-admin` token still cannot manage tokens (decision 59), and a machine still needs an admin-signed registration to be trusted by peers | Accepted, human comparison | 60, 59 |

## 7. Accepted risks

| ID | Risk | Rationale | Re-evaluate when |
|---|---|---|---|
| AR-1 | A same-user process on a machine has the user's rights there | It already has them; P-5 scope | Never accepted for policy changes (T-11) |
| AR-2 | Another app-core module, or a trojan module registered without authentication, captures the passphrase (T-13, T-14) | A malicious module already has the OS rights of the user (decision 19) | A module from an untrusted source is installed, or app-core adds authentication |
| AR-3 | While a broad right is granted, a compromised peer has that much control | Phase 1 has NO allow-all and no wildcard (decision 13) | Any wildcard, regex or allow-all capability is proposed |
| AR-4 | The relay sees metadata | Cannot be hidden without padding or mixing | Traffic analysis becomes a stated concern |
| AR-5 | Local counters can be reset by a same-user process | Same as AR-1 | Counters are used to protect against a local actor |
| AR-6 | An allowed command can disclose what it can read | The human chooses each entry | Entries are generated by something other than the human |
| AR-8 | A stolen `machine` token has full rights inside the machine scope on the relay (list presence, drop other machines' connections, flood, and PRE-BIND the uuid of another machine: the relay cannot verify the signature of an address record, so the first token to write a uuid owns its record AND its inbox; the real machine then gets `not_owner`, its inbox reads and the documents of the admin to it are suppressed. Detected loudly on the machine (not_owner notice naming the inbox), fixed by `machine admin forget-relay-record`, not prevented) and a stolen `queue` token the same for webhooks, history and listeners, including rewriting webhook signing secrets (poc-node `THREAT_MODEL.md:65`, stays open for `queue`); it never reads end-to-end encrypted traffic nor talks to a machine | The user chose "a scope gives read, write and admin on that scope" (decision 31) | Finer levels inside a scope are wanted, or a scope is shared by tokens of different trust |
| AR-7 | The encrypted admin key file is readable by same-user processes; a weak passphrase can be guessed offline. Because the admin console distributes the pair secrets (decision 22), a stolen admin key lets an attacker register a rogue machine that every peer accepts: the admin key is the root of trust and its compromise compromises the network | The user chose passphrase protection (decision 18), the simpler key model (decision 22) and a copy of the admin key on every machine (decision 23), including the work laptop whose employer policy on such a file is unknown | Any incident; a hardware authenticator becomes available (D-G option B); or the pairing ceremony is added (D-B option 2, compatible with the protocol). Passphrase chosen by the user (decision 51): at least 12 characters, a warning below 20, so the residual risk of offline guessing from a stolen machine is higher than with the generated 100-bit phrase, and ACCEPTED by the user (2026-11-15). Mitigations kept: costly KDF, `--generate` (100 bits), short unlock window, signed revocation | Note: the pair secrets of distributed pairs are derived from the admin key (T-36), so they add nothing against its theft
| AR-9 | The update channel is the siblings' one: npm registry plus publish token, no signature or provenance, automatic every 30 minutes by default. A compromised publish token or registry installs hostile code on every machine, and the daemon then runs it as the user and can open its own policy | The user asked for the same update pattern as queue, task, flow and orch (decision 38) | Before the first release if the work laptop is enrolled; npm provenance or a signature check becomes available; any incident |
| AR-10 | A stolen `machine-admin` token (relay.json and relay-admin.json of the first machine, read by its daemon, same file permissions as the other secrets, never in logs, errors or the audit log) lets the thief, with no human involved, approve or reject candidacies, REBIND a uuid to another token, and read, write and delete every inbox and every machine record on the relay. The damage stays at relay level because peers trust only admin-signed documents: an approval carries no registration the thief can sign, and the final code comparison (decision 50) still catches a swapped key. It cannot manage tokens, so it cannot mint further tokens. Detect: unexpected candidacy decisions or `not_owner` on a machine. Fix: revoke the token in the relay console, then `machine admin login --force` (and `machine join --resume` where a uuid was rebound) | The user asked for one confirmation and no second login (decision 59); the alternative (full access) is worse, and a separate admin token on the first machine only splits the file, since its daemon runs as the same user | A relay offers a scope without the inbox and machine deletion rights; the daemon of the admin machine is isolated from the admin token |

**Ping (decision 61).** `machine ping <machine>` is the first half of a `run` (the mutual TLS handshake and the revocation `hello`) with no request after it. A registered peer could already do that, so no right is added. What the target sees: nothing in its audit log when the hello is answered (`revocation.seen` updates its local record of the caller's revocation version; the caller may install, or send, admin-signed revocations, which only restrict); an older build audits one `refused unknown-message`; the per-peer limit of 6 revocation exchanges per minute is audited once a minute when exceeded, which `--count` stays under (hello in the first 4 rounds only). Up to 10 connections one second apart count against T-34 like any registered peer's. The relay form sends only `GET /api/version`, `GET /api/whoami` and the machine's own record read: no new call.

**Passphrase hint (decision 57).** The optional hint is stored in CLEAR in the admin key file and shown at every unlock prompt, so anyone who reads the file (same-user process, stolen machine, a copy of the key) reads the hint without the passphrase. It must never contain the passphrase: the tool refuses a hint that contains it (case-insensitive) but cannot judge a hint that merely makes it guessable, which lowers the cost of the offline guessing already accepted in AR-7. The hint is authenticated (part of the AEAD header): an attacker cannot swap it for a misleading one without breaking decryption, but can still delete the file. 80 printable ASCII characters only, so no control sequence reaches the terminal.

## 8. Hard rules (must not change without revisiting this model)

1. The machine daemon opens exactly two listeners: the loopback API (TB-1) and one peer listener (TB-3, decision 34), on separate servers and ports. The peer listener answers nothing before a valid first handshake message, parses nothing else pre-authentication, and is never reached by the local API. (Replaces the earlier rule "no listening port other than loopback", voided by decisions 33-34.)
2. The local loopback API and the peer channel are separate code paths; a local token never authorizes a peer request.
3. A peer request is executed only if it matches an allowlist entry byte for byte, for that peer, within its limits; no wildcard, no regex, no free command on the wire.
4. A change that widens rights (policy, registrations, pair secrets) is applied only with a valid admin signature whose base version equals the current one (compare-and-set, decision 27). Only restricting actions (cut one pair, lockdown, decision 25) need no admin signature, and they are logged.
5. The relay is never trusted: nothing it sends is acted on unless authenticated end to end; every failure is reported, never swallowed.
6. A non-encrypted or unauthenticated connection is refused (fail closed), not warned.
7. The daemon runs as the user, is never elevated, and never exposes quit or restart over the network.
8. No secret, token, passphrase or key material in logs, errors or the audit log.
9. Executed commands run with a scrubbed environment, a timeout, an output cap, without interaction.
10. An `Open` threat must not ship inside a feature that depends on it (flow's rule for T-05..T-08 [agent]).
